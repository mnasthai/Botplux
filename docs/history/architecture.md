# Plux 框架架构约束

2026-10-08，设计版本 0.1。F1–F5 已按这些约束实现，当前能力与边界见 [实现指南](implementation.md)。本文件替代原有 wechat_receiver 模块拆分约束；完整方案见 [框架设计](framework-plan.md)。

## 框架与插件

Plux（目标包 `plux`）负责原生适配、消息、数据与运行能力。所有业务通过独立插件接入。AI、记忆、广播旧实现不迁入新框架。

Python 旧接口、数据模型、插件上下文和恢复方式可以重写。旧源码作为参考，旧数据转换单独设计；外部副作用和 C++ 当前协议是需要准确处理的边界。

## 模块与依赖

| 模块 | 职责 | 允许依赖 |
| --- | --- | --- |
| `api` | 公共模型、服务约定、插件入口、上下文和错误 | 标准库及必要的 API 内部类型 |
| `data` | 数据库、事务、迁移、配置内容、资产、快照、维护 | api、明确的数据端口 |
| `messaging` | 摄取、查询、资料、媒体、输入调度和交付 | api、数据及原生端口 |
| `runtime` | 装配、注册、执行器、任务、监督、停机 | api、框架服务及组合所需适配器 |
| `adapters` | IRIS、SQLite、文件系统实现 | api、所属端口及外部实现库 |
| 独立插件 | 规则、用例、仓储、内容、展示和恢复 | plux.api、自身模块及声明的插件能力 |

api 不导入实现或业务包。框架不静态导入具体插件；启动组合按显式入口加载。插件不导入框架内部模块。公共 API 不再增加重复包装数据的服务层。

## 插件与服务

薄 Plugin 入口负责 register 及可选 start/stop，内部采用组合。PluginServices 是带插件作用域的公共能力视图；具体处理器通过小型依赖完成业务。

PluginContext 保存本次调用身份、权限、事件及有效事务作用域，不携带所有业务配置和全局服务容器。事务绑定仅在当前处理作用域有效。

配置结构、业务表、内容引用、算法、状态机及恢复政策由插件拥有。框架只管理加载、注册、存储、任务与生命周期。能力缺失、注册冲突和依赖不满足在开放业务入口前明确报告。

## 事务与副作用

原子处理器的业务变化、处理记录、任务和回复意图属于同一个数据库事务域。框架执行器拥有提交，仓储参与当前 Unit of Work。

多数据库、文件发布与外部执行采用持久步骤协调，不具有统一的跨资源回滚保证。配置读取、图片生成与文件复制在短写事务之外。

后端能力独立声明；插件仓储隔离 SQL 方言。数据驱动可扩展不等于任意数据库透明兼容。

## 身份、版本与恢复

稳定事件、处理器、任务、回复与尝试身份各有归属。平台从持久输入调度插件；重复调用和重启可识别已经提交的数据库效果。

公共插件 API、框架、快照结构、规则内容和 C++ wire 版本分别维护。规则在验证后发布不可变快照，活动任务保留创建时的规则引用。

跨消息长流程优先持久快照，插件声明恢复、条件更新、超时与结算政策。租约到期不证明外部动作未发生；副作用不确定时禁止通用自动重放。

首版 C++ v1 / JSONL 2：accepted 是本地提交事实，unknown 不自动重发；旧会话请求不改绑；执行证据追加保存。Python 停止不表示原生动作停止。

## 运行与验证

Runtime 显式装配适配器和插件，控制消费顺序、周期与后台任务、启动恢复及停机预算。资源仅在工作器真正结束后释放。首版通过配置与重启启停插件。

进程内插件是可信本地代码；处理异常可记录和隔离，不承诺恶意插件或死循环的进程隔离。

验证针对依赖方向、接口语义、失败回滚、重复消费、状态恢复、资源发布和停机。使用现有 unittest 及 C++ IPC 宿主；只有具体新数据库通过适配器检查后才声明支持。
